# Правила работы с ScenePilot

Применяются ко всему репозиторию. Пользователь — начинающий разработчик; объясняй небольшой следующий шаг простыми словами и давай конкретную проверку результата.

## Контекст и объём

- До изменений прочитай README.md, docs/roadmap.md и документы по затрагиваемой области; проверь Git-статус. Не перезаписывай чужие незакоммиченные изменения.
- Сохраняй существующий стек и рабочее приложение. Не добавляй зависимости, переписывание архитектуры или функции без конкретной необходимости.
- Выполняй согласованный шаг до проверяемого результата. Перед следующим этапом получи пользовательскую приёмку; повторное разрешение на уже согласованные действия не требуется.
- Не делегируй работу другим агентам без отдельного запроса пользователя. Этот файл содержит общие правила, а не распределение ролей между инструментами.

## Данные и секреты

- Сохраняй инварианты из docs/architecture.md: серверная проверка владельца, RLS, неизменяемые версии, снимки настроек и связь сцен с версией.
- Не читай .env.local и другие секреты без необходимости; не печатай их и не переноси в клиентский код. Для имён переменных используй .env.example.
- Не используй service_role для пользовательских операций. Не запускай облачные миграции, SQL-тесты или удаление пользовательских данных без согласованного действия.
- Не скрывай источник материала и платность реальной генерации. Ошибка модели не должна заменяться тестовым ответом.

## Расходы и внешние действия

- Не выполняй платные запросы автоматически. Бюджет Yandex: ориентир 500 ₽, максимум 1000 ₽; фактический расход пока неизвестен. Временная акция провайдера не разрешает автоматические запросы.
- Не делай автоматические повторы запросов к модели. Сохранение результата не должно повторно вызывать модель.
- Платежи, публичное размещение, изображения, аудио, видео и монтаж требуют отдельного согласования. Бюджет производства роликов не равен бюджету разработки.

## Проверки и документация

- Проверяй изменения по docs/testing.md. Тесты с подставными ответами не доказывают работу облака или визуальное качество.
- Не заявляй об успешной проверке без результата. Отмечай ограничения окружения и ручные пункты, которые остаются пользователю.
- Обновляй соответствующий документ: архитектуру, результаты проверок или план. README держи краткой входной инструкцией.
- Делай небольшие логические изменения; не смешивай несвязанные исправления. Коммиты и публикацию выполняй в согласованных пределах; секреты не коммить.
- Не объявляй приложение готовым к публичному запуску: известные ограничения перечислены в docs/testing.md и docs/roadmap.md.

Исходный материал: reference/Золотые правила vibe coding.docx. Практические правила проекта собраны здесь без привязки к конкретной IDE.
