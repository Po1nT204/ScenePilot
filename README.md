# ScenePilot

ScenePilot — учебное веб-приложение для авторов видеоконтента. Оно помогает превратить идею в сценарий, последовательность сцен, визуальные промпты и текст озвучки, сохраняя связь материалов с конкретной версией сценария.

## Статус и срок

## Локальный запуск первого каркаса

Требуется Node.js 20.19 или новее и npm. Проверяемая локальная среда: Node.js 20.19.6. Команды выполняются в папке ScenePilot.

```powershell
npm ci
npm run dev
```

Открыть http://127.0.0.1:3000. Остановка сервера: Ctrl+C в терминале. Сервер слушает только локальный интерфейс. На этом шаге ключи и аккаунты Supabase/Yandex не нужны.

Проверки кода и сборки:

```powershell
npm run lint
npm run typecheck
npm run build
```

После успешной сборки можно проверить производственный запуск командой `npm start` (предварительно остановить dev-сервер).

### Проверка пользователем

1. Открыть главную: видны ScenePilot, описание и три шага работы.
2. Нажать «Посмотреть процесс»: переход к разделу процесса. «Мои проекты» ведёт на /projects, а «Войти» — на /login.
3. Сузить окно до ширины телефона: блоки складываются в одну колонку, горизонтальной прокрутки нет.
4. Пройти ссылки клавишей Tab: фокус заметен; первая ссылка позволяет перейти к содержимому.
5. Без настройки Supabase /login, /register и /projects показывают инструкцию подключения. Генерация и CRUD проектов ещё недоступны.

Для отчёта сохранить скриншот первого экрана и узкого окна после своей проверки.

## Подключение Supabase для проверки входа

Доступ и аккаунт пользователь настраивает самостоятельно. Секреты и пароли не отправлять в чат. Для этого шага миграции и таблицы приложения ещё не нужны.

1. Открыть [панель Supabase](https://supabase.com/dashboard), войти и создать проект ScenePilot в организации на плане Free. Проверить, что выбран бесплатный план; платные опции не включать.
2. Придумать пароль базы и сохранить у себя. Этот пароль не нужен в приложении на текущем шаге.
3. Дождаться готовности проекта. В диалоге Connect скопировать Project URL и Publishable key (начинается с sb_publishable_). Не использовать secret/service_role или пароль БД. Код намеренно принимает только новый publishable-ключ.
4. Скопировать .env.example в .env.local и заполнить две переменные. Файл .env.local исключён из Git. URL и publishable-ключ публичны по назначению; приватность данных обеспечивает аутентификация и, при добавлении таблиц, RLS.
5. В Authentication → URL Configuration задать Site URL: http://127.0.0.1:3000/login. Для этой демонстрации использовать один и тот же адрес 127.0.0.1, не чередовать его с localhost.
6. Проверить, что Email provider и регистрация пользователей включены. В настройках Email для закрытой демонстрации можно отключить Confirm email. Это отдельная настройка облака, приложение её не меняет. Если оставить подтверждение включённым, после регистрации нужно подтвердить адрес по письму и затем войти; доставка писем ограничена тарифом и настройкой SMTP.
7. Перезапустить локальный сервер после изменения .env.local.

Команды в PowerShell (копирование выполняется один раз; существующий .env.local не перезаписывать):

~~~powershell
Copy-Item .env.example .env.local
npm run dev
~~~

### Проверка реального входа

- Открыть /register, создать тестовый аккаунт с паролем от 8 символов. При отключённом Confirm email ожидается переход на /projects.
- Обновить /projects: пользователь остаётся авторизованным, показан его email.
- Нажать «Выйти»: переход на /login. Повторное открытие /projects не должно показывать данные пользователя.
- Войти с неверным паролем: получить понятную ошибку без раскрытия служебных данных.
- Открыть /projects в приватном окне: ожидать перенаправление на /login.
- Зарегистрировать второй аккаунт и проверить вход и выход. Проверку доступа к чужим проектам выполним после добавления таблиц и RLS — сейчас проектов в БД нет.

До выполнения этих проверок реальная аутентификация не считается принятой. Отсутствие конфигурации показывает инструкцию, а не имитацию успешного входа.

### Устройство входа

Формы вызывают серверные действия Next.js. Сервер проверяет email и пароль, обращается к Supabase Auth и сохраняет сессию в cookie. src/proxy.ts обновляет сессию; защищённая страница дополнительно вызывает getUser, а не доверяет содержимому cookie. Персональная страница рендерится динамически. Административный ключ не используется. Библиотеки Supabase SDK 2.109.0 и SSR 0.10.0 выбраны как совместимая пара для Node.js 20.

## Цель и пользовательский сценарий

Основная ценность — связанный набор материалов для производства видео: пользователь понимает, по какой версии сценария созданы сцены и что именно экспортируется.

1. Зарегистрироваться и войти.
2. Создать проект: название, тема, жанр, язык, стиль и целевая длительность.
3. Получить сценарий от модели или ввести собственный текст.
4. Отредактировать текст и сохранить новую версию.
5. Выбрать сохранённую версию и создать сцены.
6. Проверить и отредактировать описание, визуальный промпт и текст озвучки каждой сцены.
7. Вернуться после повторного входа и продолжить работу.
8. Скопировать или экспортировать выбранную версию и её сцены в TXT или Markdown.

## Архитектура

**Next.js + TypeScript + Supabase Auth/PostgreSQL + серверная интеграция Yandex AI Studio.**

Одно приложение содержит интерфейс и серверную логику. Supabase предоставляет аутентификацию и хранение данных. Для работы с облачными сервисами нужен интернет даже при локальном запуске.

```text
Браузер пользователя
        |
        v
Next.js
  ├─ интерфейс и формы
  └─ серверные обработчики
       ├─ проверка сессии, владельца и входных данных
       ├─ проекты, версии и сцены
       ├─ экспорт TXT / Markdown
       ├─ Supabase Auth и PostgreSQL с RLS
       └─ генерация: тестовые ответы ИЛИ Yandex AI Studio
```

### Ответственность модулей

| Модуль    | Ответственность                                                 |
| --------- | --------------------------------------------------------------- |
| Интерфейс | Формы, выбор версии, отображение данных и состояний             |
| Доступ    | Проверка сессии и определение текущего пользователя             |
| Проекты   | Метаданные и принадлежность пользователю                        |
| Сценарии  | Создание и чтение неизменяемых версий                           |
| Сцены     | Материалы выбранной версии и редактирование полей               |
| Генерация | Подготовка задания, проверка результата, передача на сохранение |
| Yandex    | HTTP-запрос, секрет, тайм-аут, преобразование ошибок провайдера |
| Экспорт   | Представление одной версии и её сцен в TXT/Markdown             |

Модули — части одного приложения, не отдельные сервисы. Отдельные Express/NestJS, ORM, Redis, Docker, очереди и фоновые задачи сейчас не нужны. Новая зависимость добавляется только при конкретной необходимости.

### Основные потоки

- Создание проекта: форма → серверная проверка → владелец из сессии → БД.
- Генерация сценария: проверка доступа → настройки из БД → генератор → проверка ответа → новая версия → подтверждение сохранения.
- Генерация сцен: идентификатор версии → проверка владельца → сохранённый текст → генератор → проверка всех сцен → атомарное сохранение набора.
- Экспорт: проверка доступа → выбранная сохранённая версия и только её сцены → файл или копирование.

Режим генерации выбирается на сервере. Тестовые данные имеют отметку «Тестовые данные — модель не вызывалась». Ошибка Yandex не должна незаметно заменяться тестовым ответом. Codex помогает разрабатывать приложение; Yandex используется внутри приложения и оплачивается отдельно.

## Модель данных

Названия полей предварительные; смысл и связи обязательны.

| Сущность        | Основные поля                                                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Пользователь    | id, email, дата регистрации — в Supabase Auth                                                                                               |
| Проект          | id, owner_id, название, тема, жанр, язык, стиль, target_duration_seconds, created_at, updated_at                                            |
| Версия сценария | id, project_id, номер, текст, снимок настроек, источник сценария (manual/test/yandex), источник набора сцен (пусто/test/yandex), created_at |
| Сцена           | id, script_version_id, порядковый номер, описание, визуальный промпт, текст озвучки, updated_at                                             |

Источник показывает происхождение результата; последующая ручная правка сцен не превращает тестовую генерацию в реальную. Снимок настроек версии хранит параметры на момент её создания: изменения проекта не переписывают историю. Для него достаточно проверяемого JSON, отдельная сущность не нужна.

```text
Пользователь 1 ── N Проект
Проект       1 ── N Версия сценария
Версия       1 ── N Сцена
```

### Правила согласованности

1. Сохранённый текст и снимок настроек версии не изменяются. Редактирование создаёт новую версию.
2. Новая версия создаётся без сцен; автоматического переноса нет.
3. Один набор сцен принадлежит одной версии. Старая версия остаётся доступной для просмотра и экспорта.
4. Номер исходной версии виден рядом со сценами и в экспорте.
5. Для генерации сцен по изменённому тексту сначала нужно сохранить новую версию.
6. Переключение версии во время запроса не меняет источник результата: сохраняем у версии, с которой запрос начался.
7. Повторная генерация заменяет набор после подтверждения. Все сцены сохраняются одной транзакцией; ошибка оставляет старый набор целым.
8. Номер версии уникален в проекте, номер сцены — в версии. Внешние ключи исключают осиротевшие записи; номер версии назначается атомарно.
9. Удаление проекта после подтверждения удаляет его версии и сцены.
10. Доступ к версиям и сценам проверяется через владельца проекта.

Не добавляем таблицу операций генерации и ревизии для конфликтов редактирования. Для демонстрации используем одну вкладку на проект. Защита от потери изменений между вкладками пока не гарантируется.

## Безопасность и ошибки

Обязательны с первой реализации соответствующей функции:

- Проверять сессию и владельца на сервере; не доверять owner_id из браузера.
- Настроить RLS для проектов, версий и сцен. Проверить чтение, запись, удаление, экспорт и генерацию двумя пользователями.
- Для обычных пользовательских операций обращаться к БД с правами пользователя, не обходить RLS административным ключом.
- Секрет Yandex хранить только в серверном окружении; исключить секреты из репозитория, клиентского кода, логов и снимков экрана.
- Проверять обязательные поля, длины, длительность, число сцен и структуру ответа на сервере.
- Выводить текст без исполнения произвольного HTML. Защитить изменяющие запросы от межсайтовой отправки и исключить общий публичный кеш персональных данных.
- Отправлять в модель только необходимые настройки и текст, не email и данные аккаунта.
- Перед платными запросами задать максимальную длину входа и ответа; использовать тайм-аут.

Во время запроса блокируем повторное нажатие в текущем интерфейсе. Это не защита от повторов между вкладками. Автоматические повторы платных запросов не выполняем.

| Ситуация                           | Поведение                                                                                                                          |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Неверный ввод                      | Сообщение у поля; запрос к модели не выполняется                                                                                   |
| Истекла сессия                     | Предложение войти; по возможности сохранение текста в текущем интерфейсе                                                           |
| Yandex 401/403                     | Сообщение об ошибке настройки, без раскрытия секрета                                                                               |
| Yandex 429                         | Сообщение об ограничении, повтор по действию пользователя                                                                          |
| Тайм-аут или сеть                  | Не считать запрос гарантированно неоплаченным; не повторять автоматически                                                          |
| Пустой, оборванный, неверный ответ | Не сохранять как готовый результат; показать ошибку                                                                                |
| Ответ получен, БД недоступна       | Различать «сгенерировано» и «сохранено»; по возможности дать скопировать или повторно сохранить результат без нового вызова модели |

Диагностика содержит безопасный код ошибки, длительность и расход токенов при наличии. Полные сценарии и ключи не журналируются. Распознавание отказа по одной фразе и автоматический повтор любой ошибки не используем.

## Предварительные проверки и риски

| Риск                   | Мера                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Supabase недоступен    | Проверить до реализации входа; тестовый интерфейс не считать реальной защитой данных                                               |
| Нет доступа к Yandex   | Проверить каталог, биллинг, права, модель и короткий запрос; тестовые ответы маркировать                                           |
| Расход бюджета         | Ограничить вход/ответ, не повторять автоматически; сверять кабинет после небольших серий запросов; ориентир 500 ₽, максимум 1000 ₽ |
| Ошибки модели          | Проверять структуру; давать ручное редактирование; не обещать достоверность и точный хронометраж                                   |
| Утечка ключа           | Серверное окружение, исключение из Git и журналов; отзыв при утечке                                                                |
| Чужой доступ           | Серверная авторизация, RLS и проверки двумя аккаунтами                                                                             |
| Несогласованные версии | Неизменяемый текст, внешние ключи, явный источник, транзакция для сцен                                                             |
| Конфликты вкладок      | Для демонстрации одна вкладка; более сложную защиту добавлять при необходимости                                                    |
| Разрастание объёма     | Новые функции только после основного пути и согласования                                                                           |

Supabase: проверить доступность, тариф и возможность тестирования двумя аккаунтами. Для закрытой локальной демонстрации предложен вход по email/паролю без подтверждения email; окончательно проверить настройки перед подключением. Почтовое восстановление пока отложено.

Yandex: проверить облако, каталог, состояние платёжного аккаунта, баланс, права создания ключа, минимальные права сервисного аккаунта, область действия и срок ключа, доступную модель и текущую стоимость. Пользователь вводит секрет локально, не в чат. Подписка на помощника разработки не подтверждает доступ или оплату Yandex.

## Правила работы с ИИ и Git

- Сначала объяснять небольшой следующий шаг и способ проверки.
- Не переходить к следующему этапу без проверки и явного согласования.
- Объяснять архитектуру и код понятным языком; пользователь должен уметь защитить решения.
- Не переписывать несвязанные части и не добавлять технологии без необходимости.
- Сохранять разделение ответственности, избегать дублирования.
- Проверять после каждого изменения; важные проверки — доступ, версии, атомарность сцен и ошибки генерации.
- Не утверждать, что тесты пройдены, документ прочитан или сервис доступен без фактической проверки.
- Отделять реализованное от планируемого, тестовые ответы от реальных.
- Делать небольшие логические коммиты после проверки; не коммитить секреты.
- Возможность отката кода не равна восстановлению удалённых пользовательских данных.
- Сохранять скриншоты и результаты проверок по ходу разработки, без секретов и личных данных.
- Обновлять этот README при согласованных изменениях требований и фактическом завершении этапов.

README содержит правила как документацию. Отдельный автоматически подхватываемый файл инструкций для агента сейчас не создаётся.
