# ScenePilot

ScenePilot — учебное веб-приложение для авторов видеоконтента. Оно помогает превратить идею в сценарий, последовательность сцен, визуальные промпты и текст озвучки, сохраняя связь материалов с конкретной версией сценария.

Подготовлена серверная интеграция YandexGPT для сценария, выключенная по умолчанию. Требуется миграция источника, настройка доступа и реальный проверочный запрос; генерация сцен пока тестовая.

## Локальный запуск первого каркаса

Требуется Node.js 20.19 или новее и npm. Проверяемая локальная среда: Node.js 20.19.6. Команды выполняются в папке ScenePilot.

```powershell
npm ci
npm run dev
```

Открыть http://127.0.0.1:3000. Остановка сервера: Ctrl+C в терминале. Сервер слушает только локальный интерфейс. На этом шаге ключи и аккаунты Supabase/Yandex не нужны.

Проверки кода и сборки:

```powershell
npm run lint
npm run typecheck
npm run build
```

После успешной сборки можно проверить производственный запуск командой `npm start` (предварительно остановить dev-сервер).

### Проверка пользователем

1. Открыть главную: видны ScenePilot, описание и три шага работы.
2. Нажать «Посмотреть процесс»: переход к разделу процесса. «Мои проекты» ведёт на /projects, а «Войти» — на /login.
3. Сузить окно до ширины телефона: блоки складываются в одну колонку, горизонтальной прокрутки нет.
4. Пройти ссылки клавишей Tab: фокус заметен; первая ссылка позволяет перейти к содержимому.
5. Без настройки Supabase /login, /register и /projects показывают инструкцию подключения. Без таблицы проектов приложение предлагает выполнить миграцию. Генерация пока недоступна.

Для отчёта сохранить скриншот первого экрана и узкого окна после своей проверки.

### Файлы первого шага

## Подключение Supabase для проверки входа

Доступ и аккаунт пользователь настраивает самостоятельно. Секреты и пароли не отправлять в чат. Для этого шага миграции и таблицы приложения ещё не нужны.

1. Открыть [панель Supabase](https://supabase.com/dashboard), войти и создать проект ScenePilot в организации на плане Free. Проверить, что выбран бесплатный план; платные опции не включать.
2. Придумать пароль базы и сохранить у себя. Этот пароль не нужен в приложении на текущем шаге.
3. Дождаться готовности проекта. В диалоге Connect скопировать Project URL и Publishable key (начинается с sb_publishable_). Не использовать secret/service_role или пароль БД. Код намеренно принимает только новый publishable-ключ.
4. Скопировать .env.example в .env.local и заполнить две переменные. Файл .env.local исключён из Git. URL и publishable-ключ публичны по назначению; приватность данных обеспечивает аутентификация и, при добавлении таблиц, RLS.
5. В Authentication → URL Configuration задать Site URL: http://127.0.0.1:3000/login. Для этой демонстрации использовать один и тот же адрес 127.0.0.1, не чередовать его с localhost.
6. Проверить, что Email provider и регистрация пользователей включены. В настройках Email для закрытой демонстрации можно отключить Confirm email. Это отдельная настройка облака, приложение её не меняет. Если оставить подтверждение включённым, после регистрации нужно подтвердить адрес по письму и затем войти; доставка писем ограничена тарифом и настройкой SMTP.
7. Перезапустить локальный сервер после изменения .env.local.

Команды в PowerShell (копирование выполняется один раз; существующий .env.local не перезаписывать):

~~~powershell
Copy-Item .env.example .env.local
npm run dev
~~~

### Проверка реального входа

- Открыть /register, создать тестовый аккаунт с паролем от 8 символов. При отключённом Confirm email ожидается переход на /projects.
- Обновить /projects: пользователь остаётся авторизованным, показан его email.
- Нажать «Выйти»: переход на /login. Повторное открытие /projects не должно показывать данные пользователя.
- Войти с неверным паролем: получить понятную ошибку без раскрытия служебных данных.
- Открыть /projects в приватном окне: ожидать перенаправление на /login.
- Зарегистрировать второй аккаунт и проверить вход и выход. Проверку доступа к чужим проектам выполним после добавления таблиц и RLS — сейчас проектов в БД нет.

До выполнения этих проверок реальная аутентификация не считается принятой. Отсутствие конфигурации показывает инструкцию, а не имитацию успешного входа.

### Устройство входа

Формы вызывают серверные действия Next.js. Сервер проверяет email и пароль, обращается к Supabase Auth и сохраняет сессию в cookie. src/proxy.ts обновляет сессию; защищённая страница дополнительно вызывает getUser, а не доверяет содержимому cookie. Персональная страница рендерится динамически. Административный ключ не используется. Библиотеки Supabase SDK 2.109.0 и SSR 0.10.0 выбраны как совместимая пара для Node.js 20.

## Проекты: настройка базы и проверка

### Применение миграции

1. Открыть проект ScenePilot в Supabase → SQL Editor → New query.
2. Вставить **полное** содержимое [миграции проектов](supabase/migrations/202610120001_create_projects.sql) и выполнить Run один раз.
3. Миграция создаёт projects, ограничения полей, индекс, правила RLS и обновление updated_at. Она не изменяет аккаунты и не удаляет существующие данные. Если таблица уже существует, не удалять её: сначала проверить, применялся ли этот файл.
4. Обновить /projects в локальном приложении. При отсутствующей таблице выводится понятное сообщение; реальные операции становятся доступны после миграции.

Миграция хранится в Git для воспроизводимости. Автоматически к облачной БД агент не подключался. Файл .env.local для этого шага менять не нужно.

Сообщение «Таблица проектов ещё не настроена» означает, что приложение пока не видит таблицу projects через Supabase API. Работающий вход этого не исключает: аккаунты и таблицы приложения настраиваются отдельно. После успешного Run ожидается сообщение об успешном выполнении без возвращённых строк; в Table Editor должна появиться таблица projects. После обновления /projects ожидается пустой список с предложением создать первый проект. Если сообщение остаётся, проверить, что SQL выполнен в том же проекте Supabase, URL которого указан локально в .env.local. Ключи в чат не отправлять. Если SQL сообщает, что таблица уже существует, не запускать удаление таблицы — сначала разобраться с результатом и выбранным проектом.

### Проверка CRUD

- Под аккаунтом А создать проект: название, тема, жанр, стиль, язык, длительность.
- Открыть его из списка, изменить название и длительность, сохранить, обновить страницу.
- Выйти и войти снова: проект и правки должны сохраниться.
- Проверить пустые строки, слишком длинные поля и длительность вне диапазона 1–300 секунд. Сервер проверяет данные повторно независимо от браузера.
- Под аккаунтом Б в приватном окне открыть ссылку проекта А, включая ?edit=1: должен появиться ответ «Проект не найден», без данных А. В списке Б проект А отсутствует.
- На отдельном ненужном тестовом проекте раскрыть «Удалить проект», подтвердить удаление и проверить исчезновение из списка. Без подтверждения удаление не выполняется.
- Сохранить для отчёта скриншоты формы, карточки после правки, списка и отказа в доступе второму пользователю.

### Проверка RLS напрямую

Проверка через интерфейс не доказывает, что сама БД защищена. После создания двух тестовых аккаунтов открыть [SQL-проверку](supabase/tests/projects_rls.sql), заменить REPLACE_WITH_USER_A_UUID и REPLACE_WITH_USER_B_UUID на разные UUID из Authentication → Users и выполнить в SQL Editor целиком.

Скрипт проверяет чтение, создание, изменение и удаление для владельца, попытки другого пользователя, подмену владельца и запрет операций без входа. Тест создаёт только временный проект внутри транзакции; в конце ROLLBACK отменяет изменения. Успех — последняя строка RLS checks passed; test changes rolled back без ошибок. При ошибке проверка не пройдена; её текст можно прислать без ключей и паролей. SQL-проверка подготовлена, но агентом не выполнялась.

### Техническое устройство

- src/lib/projects/validation.ts — общие ограничения полей; сервер принимает только разрешённые поля.
- src/app/projects/actions.ts — серверные операции: владелец из getUser, фильтр owner_id, обработка ошибок и обновление страниц.
- src/app/projects/page.tsx — список текущего пользователя.
- src/app/projects/new/page.tsx — создание; src/app/projects/[id]/page.tsx — просмотр и редактирование.
- RLS в БД повторяет правило владения даже при прямом запросе API. Права на изменение owner_id, id и дат клиентам не выдаются.
- npm run test запускает тесты валидации через tsx на Node.js 20. Эти тесты не заменяют проверку реальной БД.

## Ручные версии сценария: настройка и проверка

Редактор и история проверены пользователем. При настройке новой базы в Supabase → SQL Editor → New query выполнить целиком [миграцию версий](supabase/migrations/202610130001_create_script_versions.sql) один раз после миграции проектов, затем остальные миграции по порядку. Уже применённые миграции не повторять.

Локальная проверка 13 октября: npm run build (включая TypeScript), npm run lint и все 9 тестов npm run test прошли. Проверка реального сохранения и SQL-теста в Supabase, а также визуальная приёмка редактора ещё не выполнены.

1. Открыть проект → «Открыть сценарий», ввести текст, сохранить. Ожидается версия 1.
2. Изменить текст, сохранить. Ожидается версия 2; открыть версию 1 и проверить, что её текст прежний. Перезагрузка и повторный вход не теряют версии.
3. Изменить тему в настройках проекта. В старой версии раскрыть «Настройки на момент сохранения»: тема остаётся прежней. Изменить текст и сохранить новую версию — она получает новые настройки.
4. Набрать несохранённый текст и нажать ссылку другой версии: появляется подтверждение ухода. Черновики не сохраняются автоматически. Предупреждение работает для ссылок и закрытия/перезагрузки вкладки; кнопки браузера «Назад/Вперёд» при переходе внутри приложения могут не вызвать предупреждение. Перед ними сохранить текст или скопировать его.
5. Под вторым пользователем открыть полный адрес сценария первого: данные недоступны. Прямую проверку прав выполнить через [SQL-тест версий](supabase/tests/script_versions_rls.sql), подставив UUID двух тестовых аккаунтов. Тест проверяет неизменяемость, снимки, доступ, валидацию и каскадное удаление; изменения откатываются. Агент этот SQL-тест в облаке не выполнял.

Таблица script_versions хранит project_id, уникальный номер внутри проекта, content (до 20 000 символов), settings_snapshot, created_at, id и после миграции 202610130003 — source. Функция save_script_version проверяет владельца, блокирует строку проекта на время сохранения, назначает номер и сохраняет снимок настроек одной транзакцией. Клиент не назначает номера и не пишет в таблицу напрямую. Изменение и отдельное удаление версий запрещены; удаление проекта удаляет его версии.

Для отчёта сохранить две версии с разным текстом, старый снимок после изменения проекта и отказ доступа второму аккаунту. Точка Git: отдельный коммит ручных версий после проверки. Следующий шаг после приёмки — явно обозначенная тестовая генерация.

### Тестовый сценарий

Проверено 13 октября: сборка с TypeScript, ESLint, git diff --check и все 12 тестов прошли. Интерактивная проверка нового сценария пользователем ещё ожидается.

Новая миграция и ключ Yandex для этого шага не нужны. В редакторе доступна кнопка «Получить тестовый пример». Сервер проверяет пользователя и владельца проекта, читает текущие настройки и собирает детерминированную заготовку: вступление, основная часть и завершение. Это шаблон с инструкциями автору, а не результат работы языковой модели. Жанр, стиль и длительность указаны как ориентиры; точный хронометраж не рассчитывается. Для английского проекта инструкции будут английскими, введённая тема не переводится.

Результат попадает только в редактор. Сохранение новой версии — отдельное действие. Повторная генерация требует подтверждения замены непустого текста; отказ или ошибка сохраняют прежний текст. Во время запроса редактор и кнопки блокируются. При тех же настройках результат будет одинаковым. После тестовой генерации интерфейс показывает источник «тестовый шаблон», в текст добавляется явный заголовок тестового примера. Заголовок можно редактировать как обычный текст; отдельное поле source сохраняет источник независимо от заголовка.

Проверка:

1. Открыть сценарий проекта и получить пример: настройки присутствуют, есть тестовая отметка и сообщение «ещё не сохранён»; новая версия в истории не появляется автоматически.
2. Исправить текст и сохранить новую версию; обновить страницу и открыть прежнюю версию — её текст не изменился.
3. Набрать несохранённую правку, нажать получение примера и отменить подтверждение: правка остаётся.
4. Подтвердить замену: новый пример появляется в редакторе, но не сохраняется сам.
5. Проверить английский проект. Для отчёта сохранить тестовую отметку, результат до сохранения и новую версию в истории.

Следующий шаг после приёмки — сцены, привязанные к выбранной сохранённой версии. Git: отдельный коммит тестового генератора после проверки.

## Проверка сцен (текущий шаг)

Локально 13 октября прошли сборка с TypeScript, ESLint, git diff --check и 16 тестов. Визуальная проверка карточек и выполнение миграции/SQL-тестов в Supabase ожидаются; локальные тесты не доказывают работу облачных прав доступа.

В Supabase → SQL Editor → New query выполнить целиком [миграцию сцен](supabase/migrations/202610130002_create_scenes.sql) один раз. Старые миграции не повторять. Таблица scenes связана с script_versions; права чтения ограничены владельцем проекта. Запись разрешена только через save_test_scenes: функция повторно проверяет владельца, проверяет весь набор и атомарно заменяет сцены одной версии. При ошибке старый набор остаётся целым. Поле source всегда test и не меняется после ручной правки. Удаление проекта каскадно удаляет версии и сцены.

1. Открыть сохранённый сценарий → «Сцены версии N». Номер версии виден над редактором; исходный текст раскрывается отдельно.
2. Нажать «Подготовить тестовые сцены». Абзацы разделяются на сцены; слишком длинный текст разбивается механически. Ограничение — 1–12 сцен, до 2000 символов на поле. Это не смысловой анализ: служебный текст тестового сценария тоже попадёт в озвучку, его нужно отредактировать.
3. Изменить описание кадра, визуальный промпт и озвучку, нажать «Сохранить сцены», обновить страницу. Все правки должны сохраниться.
4. Сохранить новую версию сценария и открыть её сцены: список пустой. Вернуться к старой версии — прежние сцены на месте.
5. Повторно подготовить тестовые сцены: сначала подтверждение замены редактора, затем отдельное сохранение. Пока не нажато сохранение, набор в БД прежний. При ошибке запроса текст в редакторе остаётся.
6. Проверить адрес сцен аккаунтом Б: чужой набор недоступен. [SQL-тест сцен](supabase/tests/scenes_rls.sql) с UUID двух тестовых аккаунтов проверяет RLS, запрет прямой записи, атомарность, привязку к версии и каскадное удаление. Все тестовые изменения откатываются; агент в облаке тест не выполнял.

Несохранённые правки защищены предупреждением при клике по ссылке и перезагрузке/закрытии. Кнопки браузера «Назад/Вперёд» могут обойти предупреждение при переходе внутри приложения. Для демонстрации используем одну вкладку на проект; сохранение из другой вкладки может заменить набор. История правок сцен и изменение порядка пока не реализуются.

Для отчёта: карточки сцен с номером версии, правки после перезагрузки и пустой набор новой версии. Git: отдельный коммит сцен после проверки. После приёмки можно переходить к проверке доступа Yandex и реальной генерации.

### Один проверочный запрос

После подтверждения условий: короткая тема, длительность 30–60 секунд → «Сгенерировать с YandexGPT» → подтвердить платный запрос. Ожидается связный текст озвучки без инструкций автору. Интерфейс показывает число токенов, если оно пришло в ответе. Проверить факты и язык, сохранить версию и перезагрузить. Источник YandexGPT должен сохраниться. После одного запроса проверить расход в биллинге, учитывая возможную задержку его отображения. Ошибка не должна менять прежний текст; неполный или пустой ответ не принимается. Сохранение повторяется без нового вызова модели.

Источник хранится неизменно для сохранённой версии; редактирование наследует источник, новый тестовый/реальный запрос заменяет его. Это метаданные учебного интерфейса, а не криптографическое доказательство происхождения: авторизованный клиент может указать допустимый источник при сохранении. Старые версии не переименовываются автоматически в ручные или тестовые. SQL-функция внутреннего сохранения закрыта от вызова пользователями.

Для отчёта сохранить реальный ответ с источником, номером версии и токенами, результат повторного входа, расход без секретов. Новые зависимости не нужны. Git: отдельный коммит серверной интеграции после проверки. Реальную генерацию сцен подключаем после проверки сценария.

## Архитектура

**Next.js + TypeScript + Supabase Auth/PostgreSQL + серверная интеграция Yandex AI Studio.**

Одно приложение содержит интерфейс и серверную логику. Supabase предоставляет аутентификацию и хранение данных. Для работы с облачными сервисами нужен интернет даже при локальном запуске.

```text
Браузер пользователя
        |
        v
Next.js
  ├─ интерфейс и формы
  └─ серверные обработчики
       ├─ проверка сессии, владельца и входных данных
       ├─ проекты, версии и сцены
       ├─ экспорт TXT / Markdown
       ├─ Supabase Auth и PostgreSQL с RLS
       └─ генерация: тестовые ответы ИЛИ Yandex AI Studio
```

### Ответственность модулей

| Модуль    | Ответственность                                                 |
| --------- | --------------------------------------------------------------- |
| Интерфейс | Формы, выбор версии, отображение данных и состояний             |
| Доступ    | Проверка сессии и определение текущего пользователя             |
| Проекты   | Метаданные и принадлежность пользователю                        |
| Сценарии  | Создание и чтение неизменяемых версий                           |
| Сцены     | Материалы выбранной версии и редактирование полей               |
| Генерация | Подготовка задания, проверка результата, передача на сохранение |
| Yandex    | HTTP-запрос, секрет, тайм-аут, преобразование ошибок провайдера |
| Экспорт   | Представление одной версии и её сцен в TXT/Markdown             |

Модули — части одного приложения, не отдельные сервисы. Отдельные Express/NestJS, ORM, Redis, Docker, очереди и фоновые задачи сейчас не нужны. Новая зависимость добавляется только при конкретной необходимости.

### Основные потоки

- Создание проекта: форма → серверная проверка → владелец из сессии → БД.
- Генерация сценария: проверка доступа → настройки из БД → генератор → проверка ответа → новая версия → подтверждение сохранения.
- Генерация сцен: идентификатор версии → проверка владельца → сохранённый текст → генератор → проверка всех сцен → атомарное сохранение набора.
- Экспорт: проверка доступа → выбранная сохранённая версия и только её сцены → файл или копирование.

Режим генерации выбирается на сервере. Тестовые данные имеют отметку «Тестовые данные — модель не вызывалась». Ошибка Yandex не должна незаметно заменяться тестовым ответом. Codex помогает разрабатывать приложение; Yandex используется внутри приложения и оплачивается отдельно.

## Модель данных

Названия полей предварительные; смысл и связи обязательны.

| Сущность        | Основные поля                                                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Пользователь    | id, email, дата регистрации — в Supabase Auth                                                                                               |
| Проект          | id, owner_id, название, тема, жанр, язык, стиль, target_duration_seconds, created_at, updated_at                                            |

Источник показывает происхождение результата; последующая ручная правка сцен не превращает тестовую генерацию в реальную. Снимок настроек версии хранит параметры на момент её создания: изменения проекта не переписывают историю. Для него достаточно проверяемого JSON, отдельная сущность не нужна.

```text
Пользователь 1 ── N Проект
Проект       1 ── N Версия сценария
Версия       1 ── N Сцена
```

### Правила согласованности

1. Сохранённый текст и снимок настроек версии не изменяются. Редактирование создаёт новую версию.
2. Новая версия создаётся без сцен; автоматического переноса нет.
3. Один набор сцен принадлежит одной версии. Старая версия остаётся доступной для просмотра и экспорта.
4. Номер исходной версии виден рядом со сценами и в экспорте.
5. Для генерации сцен по изменённому тексту сначала нужно сохранить новую версию.
6. Переключение версии во время запроса не меняет источник результата: сохраняем у версии, с которой запрос начался.
7. Повторная генерация заменяет набор после подтверждения. Все сцены сохраняются одной транзакцией; ошибка оставляет старый набор целым.
8. Номер версии уникален в проекте, номер сцены — в версии. Внешние ключи исключают осиротевшие записи; номер версии назначается атомарно.
9. Удаление проекта после подтверждения удаляет его версии и сцены.
10. Доступ к версиям и сценам проверяется через владельца проекта.

Не добавляем таблицу операций генерации и ревизии для конфликтов редактирования. Для демонстрации используем одну вкладку на проект. Защита от потери изменений между вкладками пока не гарантируется.

## Безопасность и ошибки

Обязательны с первой реализации соответствующей функции:

- Проверять сессию и владельца на сервере; не доверять owner_id из браузера.
- Настроить RLS для проектов, версий и сцен. Проверить чтение, запись, удаление, экспорт и генерацию двумя пользователями.
- Для обычных пользовательских операций обращаться к БД с правами пользователя, не обходить RLS административным ключом.
- Секрет Yandex хранить только в серверном окружении; исключить секреты из репозитория, клиентского кода, логов и снимков экрана.
- Проверять обязательные поля, длины, длительность, число сцен и структуру ответа на сервере.
- Выводить текст без исполнения произвольного HTML. Защитить изменяющие запросы от межсайтовой отправки и исключить общий публичный кеш персональных данных.
- Отправлять в модель только необходимые настройки и текст, не email и данные аккаунта.
- Перед платными запросами задать максимальную длину входа и ответа; использовать тайм-аут.

Во время запроса блокируем повторное нажатие в текущем интерфейсе. Это не защита от повторов между вкладками. Автоматические повторы платных запросов не выполняем.

| Ситуация                           | Поведение                                                                                                                          |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Неверный ввод                      | Сообщение у поля; запрос к модели не выполняется                                                                                   |
| Истекла сессия                     | Предложение войти; по возможности сохранение текста в текущем интерфейсе                                                           |
| Yandex 401/403                     | Сообщение об ошибке настройки, без раскрытия секрета                                                                               |
| Yandex 429                         | Сообщение об ограничении, повтор по действию пользователя                                                                          |
| Тайм-аут или сеть                  | Не считать запрос гарантированно неоплаченным; не повторять автоматически                                                          |
| Пустой, оборванный, неверный ответ | Не сохранять как готовый результат; показать ошибку                                                                                |
| Ответ получен, БД недоступна       | Различать «сгенерировано» и «сохранено»; по возможности дать скопировать или повторно сохранить результат без нового вызова модели |

Диагностика содержит безопасный код ошибки, длительность и расход токенов при наличии. Полные сценарии и ключи не журналируются. Распознавание отказа по одной фразе и автоматический повтор любой ошибки не используем.

1. Вход и регистрация.
2. Мои проекты: список, пустое состояние, создание, открытие и удаление.
3. Настройки проекта.

История версий размещается в рабочей области, отдельный экран не требуется.

## Этапы разработки и приёмка

Даты — ориентир, переход между этапами требует проверки и явного согласования пользователя. Внутри этапа выполняется одна небольшая проверяемая задача за раз.

### 1. Документация и предпосылки — 12–13 октября

- [x] Получить приёмку документации.

## Предварительные проверки и риски

| Риск                   | Мера                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Supabase недоступен    | Проверить до реализации входа; тестовый интерфейс не считать реальной защитой данных                                               |
| Нет доступа к Yandex   | Проверить каталог, биллинг, права, модель и короткий запрос; тестовые ответы маркировать                                           |
| Расход бюджета         | Ограничить вход/ответ, не повторять автоматически; сверять кабинет после небольших серий запросов; ориентир 500 ₽, максимум 1000 ₽ |
| Ошибки модели          | Проверять структуру; давать ручное редактирование; не обещать достоверность и точный хронометраж                                   |
| Утечка ключа           | Серверное окружение, исключение из Git и журналов; отзыв при утечке                                                                |
| Чужой доступ           | Серверная авторизация, RLS и проверки двумя аккаунтами                                                                             |
| Несогласованные версии | Неизменяемый текст, внешние ключи, явный источник, транзакция для сцен                                                             |
| Конфликты вкладок      | Для демонстрации одна вкладка; более сложную защиту добавлять при необходимости                                                    |
| Разрастание объёма     | Новые функции только после основного пути и согласования                                                                           |

Supabase: проверить доступность, тариф и возможность тестирования двумя аккаунтами. Для закрытой локальной демонстрации предложен вход по email/паролю без подтверждения email; окончательно проверить настройки перед подключением. Почтовое восстановление пока отложено.

Yandex: проверить облако, каталог, состояние платёжного аккаунта, баланс, права создания ключа, минимальные права сервисного аккаунта, область действия и срок ключа, доступную модель и текущую стоимость. Пользователь вводит секрет локально, не в чат. Подписка на помощника разработки не подтверждает доступ или оплату Yandex.

## Правила работы с ИИ и Git

- Сначала объяснять небольшой следующий шаг и способ проверки.
- Не переходить к следующему этапу без проверки и явного согласования.
- Объяснять архитектуру и код понятным языком; пользователь должен уметь защитить решения.
- Не переписывать несвязанные части и не добавлять технологии без необходимости.
- Сохранять разделение ответственности, избегать дублирования.
- Проверять после каждого изменения; важные проверки — доступ, версии, атомарность сцен и ошибки генерации.
- Не утверждать, что тесты пройдены, документ прочитан или сервис доступен без фактической проверки.
- Отделять реализованное от планируемого, тестовые ответы от реальных.
- Делать небольшие логические коммиты после проверки; не коммитить секреты.
- Возможность отката кода не равна восстановлению удалённых пользовательских данных.
- Сохранять скриншоты и результаты проверок по ходу разработки, без секретов и личных данных.
- Обновлять этот README при согласованных изменениях требований и фактическом завершении этапов.

README содержит правила как документацию. Отдельный автоматически подхватываемый файл инструкций для агента сейчас не создаётся.
